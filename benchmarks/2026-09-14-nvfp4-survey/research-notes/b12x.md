## Candidate to prioritize

The standalone **NVFP4 W4A16 dense path** is directly relevant to 27B decode
and speculative verification. It reads the same packed FP4 checkpoint payload
and E4M3 block scales as W4A4, while retaining BF16 activations and dequantizing
weights inside the compute kernel. There is no activation quantization launch
or activation-global-scale math in W4A16. This is a distinct computation from
checkpoint-calibrated W4A4 and needs its own quality label/reference.

Concrete public entrypoints:

- `b12x.gemm.blockscaled.w4a16(x, packed_w, swizzled_sf, global_scale, out=out,
  workspace=scratch, global_scale_kind="multiplier", _config=(128,64,4))`.
- `weight = blockscaled.pack_weight(packed_w, swizzled_sf, recipe="nvfp4",
  global_scale=weight_scale_2)` then `blockscaled.mm(x, weight, mode="a16", ...)`.
- The same `weight` supports `mode="quantized"`, with
  `activation_global_scale=input_scale.reciprocal()` for a checkpoint whose
  `input_scale` is the dequant multiplier. Explicitly verify that convention
  against the exact checkpoint loader. This argument is the quantizer multiplier.
- For prequantized inputs: `blockscaled.mm_nvfp4(a_packed, a_sf_swizzled,
  w_packed, w_sf_swizzled, alpha)` where `alpha = activation_dequant_global *
  weight_dequant_global`.

Sources: `gemm/blockscaled/api.py`, `_a16.py`, `_linear.py`, `_quantize.py`.

## Layout and math contract

- BF16 input `[M,K]`, packed uint8 weights `[N,K/2]`; low nibble is even K and
  high nibble odd K, signed E2M1 values `{0,.5,1,1.5,2,3,4,6}`.
- E4M3 scale for each contiguous K/16 group. Weight reconstruction is
  `E2M1 * E4M3 * global_scale` for multiplier mode; reciprocal mode divides by
  the global. Dense W4A16's local dequantization rounds to BF16 before BF16 MMA.
- Shared scale storage is F8_128x4, physically padding N to128 and K/16 to4.
  Its byte offset for row r, group g, G=K/16 is
  `((r//128)*ceil(G/4)+g//4)*512 + (r%32)*16 + ((r//32)%4)*4 + g%4`.
  Padding must be initialized. No weight-value repack is needed for this path;
  swizzling block scales is one load-time transformation.
- All pointers contiguous,16-byte aligned, same CUDA device. A16 requires
  K%32=0, inputK%8=0,N%8=0; quantized path K%128=0,N%8=0. Relevant 27B dense
  shapes meet these alignment requirements.
- A16 output BF16, optional split-K partials FP32. `(Ntile,Ktile,splitK)` choices:
  Ntile64/128,Ktile64/128,splitK1/2/4/8. Runtime caps splitK by ceil(K/Ktile).
  Scratch for splitK is `4*splitK*M*N` bytes, then one reduction kernel.
- The default precision heuristic selects A16 for M1..8 with `(128,64,4)`;
  M16 falls to quantized unless explicitly forced. This is a heuristic,
  not evidence that A16 is worse at16 on GB10/Qwen shapes. Race both.
- A16 physical M tile is16. W4A4 dense often uses64-row tiles at smallM.
  Small-M occupancy and weight-bandwidth utilization are key uncertainties.

The W4A4 activation quantizer computes E4M3 sf from local amax/6 times the
quantizer multiplier, divides by the rounded sf to produce E2M1, and writes
swizzled scales plus output alpha. Thus collapsing globals into FP8 scales
changes rounding/underflow and cannot generally preserve exact math.

## AOT integration

b12x's Python facade owns policy, validation, allocation, and JIT caching and
is unsuitable as an inference dependency under qs3's AOT boundary. Its actual
compute launch has a usable lower boundary:

- `_lib/dense_gemm.py::_DenseGemmLaunch`, `cute.jit`, takes typed device pointers,
  live M and CUstream; N/K/layout/tile/split static at construction.
- `DenseGemmKernel` owns TMA load setup and BF16/blockscaled tensor MMA.
- `_DenseSplitKReduce` is a separate `cute.jit` launcher over two pointers,M,stream.
- Existing `_lib/compiler.py` already calls `dump_to_object` and persists native
  compiled host launch objects. Export those launchers through CuTe's
  `JitCompiledFunction.export_to_c(file_path=...,file_name=...,function_prefix=...)`.
  This produces a C header and object; link the object plus CUDA runtime from
  a small kernel-glue TU. Rust can own output/scratch and static-plan selection.
- Retain generated host launch code initially because it constructs TMA
  descriptors. Extracting cubins and hand-reconstructing their launch arguments
  would add avoidable risk. Compile on ARM64sp10 first; host crosscompile to
  linux-aarch64 is a separate qualification item.
- W4A4 adds an AOT Triton quantizer or equivalent existing CUDA quantizer that
  writes exactly the same layout; A16 only needs compute+optionalreduce objects.
- First milestone: export one27B MLP shape, link native executable, compare
  native output with the already qualified Python invocation, then measure
  both to separate Python dispatch gaps from compute.

This is feasibility supported by source and export API, **not an already
tested native export**. Official CuTe AOT documentation:
https://docs.nvidia.com/cutlass/4.5.2/media/docs/pythonDSL/cute_dsl_general/dsl_ahead_of_time_compilation.html

## MoE and vLLM distinctions

Pinned standalone b12x includes native-weight MoE W4A16 direct and tensor-core
paths. `moe/_shared/kernels/w4a16/prepare.py::prepare_w4a16_modelopt_native_weights`
retains FP4 payload,swizzledE4M3scales,rawweightglobals. Public
`moe.fused_moe.plan_weights` accepts sourceformat=`modelopt_nvfp4`; force
SOURCE_NATIVE packing to avoid conflating repacking costs or numericalchanges.
Direct W4A16 routing is limited to<=8tokens;16 needs packedrouting. Its
`benchmarks/benchmark_nvfp4_decode_precisions.py` already races A4/A16 using
the same checkpoint payload and verifies shared pointers. It is MoE-specific,
not the dense probe. Route pooling and expert layout are additional integration
work; prioritize27B dense first before porting the complete MoE planner.

The older vendored vLLM `experts/flashinfer_b12x_moe.py` is **not** equivalent
to this standalone native path. Its post-load adapter multiplies
`weight_scale_2` into E4M3 scales then sets globals to1, and replaces calibrated
FC2 activation scale with1. The comment claiming identical dequantized results
cannot hold for arbitrary non-power-of-two multipliers and finite E4M3 range.
Avoid using that adapter as an exact checkpoint oracle without checking the
transformed quantized math.

Newer upstream vLLM0.29 documents distinct native `--linear-backend b12x` and
`--moe-backend b12x`, NVFP4MoE checkpoint activation format with an A16 override,
and explicitly excludes denseW4A16 integration. That exclusion is vLLM's
adapter scope; standalone b12x here does have the denseA16kernel.
https://docs.vllm.ai/en/v0.29.0/features/quantization/b12x/
Its native NVFP4 linear adapter preserves globals: calls scaled_fp4_quant using
input_global_scale_inv, then blockscaled.mm_nvfp4 using layer.alpha; only
load-time scaleswizzle:
https://raw.githubusercontent.com/vllm-project/vllm/v0.29.0/vllm/model_executor/kernels/linear/nvfp4/b12x.py

### Follow-up MoE probe

`moe_probe.py --output DIR` prepares full synthetic Qwen35B routed experts:
E256, H2048, I512, top8; M1/2/4/5/16. Each precision runs in its own sequential
subprocess. This isolates CUDA faults and records individual errors without
preventing the other precision from running. The source-native AUTO weight plan
is necessary: explicit uniform A16 preparation requires a different packed
representation. Explicit execution policy then selects A16 direct routing for
M<=8, A16 packed routing for M16, A4 micro for M<=8, and A4 grouped dynamic for16.

Timing uses the shared graph-free event harness and includes internal route
dispatch, gate/up, SiLU, down, and weighted expert reduction. It excludes the
router-logit projection and top-k selection (IDs and weights are inputs), the
shared expert, setup, allocation and compilation. `--routing shared` reuses the
same eight experts across tokens; default diverse routing spreads requests.
Both references expand only selected expert routes, never the full E256 BF16
weight bank. Quality gates run before timing and reports retain raw errors.

This is synthetic evidence only. Real checkpoint adapter issue found in the
upstream Qwen benchmark loader: it reads gate globals but does not read or
validate the corresponding up globals before concatenating the two matrices.
Our loader must check gate/up global equality before passing one fused W13
global per expert. Unequal globals need separate projections or an explicitly
validated conversion, not silent use of the gate global for both halves.


## Exact NVIDIA checkpoint precision audit

The name NVFP4 does not determine activation precision. Read the pinned
ModelOpt `quantized_layers` map and retain that precision in the model plan.
The current NVIDIA 35B and 3.8-27B checkpoints differ:

| Checkpoint | Exact revision | ModelOpt layer map |
| --- | --- | --- |
| nvidia/Qwen3.6-35B-A3B-NVFP4 | `6c7f09d4036e97393f82e9f9ecd1a5c35ca5ee92` | 161 W4A16_NVFP4 entries; 130 FP8 entries |
| nvidia/Qwen3.8-27B-NVFP4 | `dbb8f445b3145f8a4c18ddc769f032d57d32867c` | 193 NVFP4/W4A4 entries; 208 FP8 entries |

The 35B config fetched from the exact upstream revision is parsed-JSON
identical to root's cached config; this is not an accidental local edit.
Raw config length 58,110 bytes, SHA256
`58aefa1c9eff7989f431d748f2ddec39446cb1fd2a69acc46e285c6a37b0cecc`.
Its stale compressed-tensors `config_groups` still describes input4/weight4,
but `quant_method=modelopt`, `quant_algo=MIXED_PRECISION`, and the per-layer
map select W4A16. Its producer field says ModelOpt0.37.0. The model card's
prose and tool-version text are less specific than the per-layer config; the
card explicitly recommends Marlin MoE on DGX Spark.

The 3.8-27B config and separate `hf_quant_config.json` agree on all layer
algorithms: 64x3 MLP projections plus LM head use NVFP4/W4A4; 208 attention
and GDN projections use FP8. Config length87,506, SHA256
`71fa01bb64de20971045cd82a82c0ebb25a54e1b0a3f09ef23cf5479e9c54df8`;
hf_quant_config length53,760, SHA256
`5f4aaa9e462ddb26a9790ab459eee69d100b9ade7541f0c86038e925c013f80b`.
Its producer field is ModelOpt0.47.0.dev80+g913f5e224. The revision was resolved
from the public Hugging Face model API on2026-09-14 and both exact raw files
are preserved beside this note.

In vendored vLLM `modelopt.py`, `ModelOptMixedPrecisionConfig` prefers the
ModelOpt `quantized_layers` map and dispatches W4A16 to its own linear config.
`ModelOptNvFp4W4A16LinearMethod` explicitly selects Marlin, drops the optional
`input_scale` checkpoint placeholder, and retains `weight_scale_2` as a
**dequantization multiplier**, without reciprocation. Its MoE counterpart
passes activation_key=None, which excludes W4A4 implementations. This explains
how a W4A4-shaped tensor inventory can still specify W4A16 execution.

Therefore grade the experiments in two dimensions: kernel correctness against
same-precision dequantized operands, then end-to-end quality against the
checkpoint's declared activation precision. W4A4 on this 35B and W4A16 on this
3.8-27B change execution precision; neither is a drop-in correctness claim.
BF16 activations are not automatically interchangeable with calibrated FP4
activations merely because the weight bytes are identical.

Fusion warning: vendored W4A16 linear warns when fused partitions have unequal
weight globals, then takes their maximum without compensating the payload.
Do not use that approximation as a correctness oracle. Quasar should preserve
separate projections or require equal globals for the proposed fused W13
contract. b12x's benchmark likewise reads the gate global without validating
up global, so root's real-tensor scale audit is required.
